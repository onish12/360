as the driver's LINE/MSI decision.

## PCI interrupt capability properties

The captured device properties report:

- `DEVPKEY_PciDevice_InterruptSupport = 3`;
- `DEVPKEY_PciDevice_InterruptMessageMaximum = 1`.

Windows pciprop.h defines InterruptSupport as a bitmask:
LineBased=1, Msi=2, MsiX=4. Value 3 therefore proves hardware support for
line-based and MSI, with no MSI-X support bit declared. MessageMaximum=1 proves
the hardware reports at most one message interrupt.

This capability evidence does not force the future driver to use MSI. The
future PnP path must classify the actual assigned raw/translated
CM_PARTIAL_RESOURCE_DESCRIPTOR pair using CM_RESOURCE_INTERRUPT_MESSAGE.

## Admission consequence

The next safe software-only milestone may admit a single assigned interrupt pair
without hard-coding its signaling mode:

- exactly one assigned interrupt descriptor pair;
- raw/translated kind must agree (already enforced by M0.6.15E);
- line-based is admissible;
- message-signaled is admissible only when raw MessageCount == 1;
- zero or multiple assigned interrupt pairs fail closed;
- MSI with MessageCount > 1 fails closed for this hardware contract;
- no vector, level, affinity, share disposition or negative ConfigMgr IRQ number
  is hard-coded.

This admission step does not call WdfInterruptCreate and does not touch
hardware.

## Evidence limits

The F4 user-mode IRQ_RESOURCE format does not expose the kernel
CM_RESOURCE_INTERRUPT_MESSAGE bit. The current Intel driver's allocation is
strongly consistent with a message-signaled interrupt (edge-triggered, negative
display IRQ, and hardware MSI capability), but that interpretation is not used
as a production invariant.

The definitive signaling kind for the custom driver will come from the
raw/translated CM_PARTIAL_RESOURCE_DESCRIPTOR pair delivered to its own
PrepareHardware path.

No DSP boot, codec/amplifier programming or playback is authorized by this
evidence.
