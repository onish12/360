# Audit PHASER360 M1 R7 și corecție R8 candidat

Data: 26 septembrie 2026. Bază de cod: `onish12/360`, commit `7508b1f2ee38c3461382fc366e26b5bf3b7d348f`.

**Verdict actualizat:** blocajul imediat al execuției R7 este demonstrat: verificarea obligatorie a revenirii biților SSP expiră înaintea comenzii către ROM. Corecția și regresia au fost implementate. Commitul R8 `be2e17a720adb49583f9fd7a75cc0cec39b33a45` a trecut compilarea WDK, testele Windows și verificarea pachetului semnat. Există acum un candidat binar pentru proba M1; DSP-ul funcțional și sunetul nu sunt încă demonstrate pe dispozitiv.

Auditul acoperă rezultatul primit, pachetul R7 corespunzător, lanțul M1 de instalare–PnP–alimentare–ROM–DMA–IPC–rollback, testele portabile, workflow-ul de pachet și afirmațiile relevante din documentația proiectului. Componentele istorice sunt delimitate de calea M1 curentă; nu am executat fizic etapele arhivate. Corecțiile sunt publicate pe ramura izolată `codex/m1-r8-ssp-contract-20260926`. Nu am instalat drivere pe calculatorul țintă și nu am executat playback, programare codec, activare speaker, modificări BCD ori reboot.

## De ce a eșuat R7

În toate cele șase încercări, prima eroare este aceeași:

```text
G75_ROM_CONFIGURE_SSP_FAIL status=0xC0000182 value=0x00000000
G7E_ROM_ERR_TIMEOUT
G70_ROM_INITIALIZE_FAIL
D40_FIRMWARE_ENTER_FAIL
```

Înaintea ei sunt confirmate pregătirea HDA, alocarea și pregătirea bufferelor, configurarea streamului oprit, politica PCI, oprirea inițială a core-urilor și armarea IPC. Sursa execută apoi, pentru șase porturi SSP, o actualizare mascată urmată de un `Poll(..., 50000)` obligatoriu. Masca așteptată este `0x03000000`. Ultima valoare raportată este zero, iar codul abandonează operația.

Această ramură precede scrierea `HIPCI ROM_CONTROL/PURGE`. Transferul firmware, pornirea HDA RUN, `FW_ENTERED` și `FW_READY` nu sunt atinse. `0xC0000182` este `STATUS_DEVICE_CONFIGURATION_ERROR`, returnat de wrapper; nu este un cod de respingere criptografică produs de firmware [S8].

În implementarea Linux APL/GLK consultată, `hda_ssp_set_cbp_cfp()` face actualizările mascate, fără a condiționa continuarea de un polling al revenirii acestor biți. Confirmările efective ale pornirii vin ulterior din protocolul ROM [S1–S3]. Adresele din R7 sunt corecte conform acestor surse: `0x2004`, `0x3004`, `0x4004`, `0x5004`, `0x6004`, `0x7004`. Nu există aici justificare pentru mutarea bazei la `0x20000`.

**Ce știm:** condiția software care oprește R7 și nepotrivirea ei față de secvența upstream. **Ce nu știm:** de ce registrul citit pe acest dispozitiv revine cu zero și care port exact a produs eșecul. R7 nu înregistrează indexul/offsetul. Nu presupun SSP0 și nu declar că eliminarea acelui polling garantează succesul etapelor următoare.

Eroarea finală `WIN32_ERROR=259` înseamnă că enumerarea nu mai are o interfață disponibilă. În contextul acestui log, ea apare după eșecul pornirii driverului. Code 10 semnifică failed start; KMDF activează interfețele când dispozitivul pornește și le dezactivează la eliminare [S4, S5, S11]. Aceasta explică de ce schimbarea mecanismului de enumerare sau mărirea așteptării de telemetrie nu repară etapa G75.

## Probleme constatate și rezolvarea propusă

| Prioritate | Constatare | Modificare / stare |
|---|---|---|
| P0 | Polling SSP suplimentar blochează înainte de ROM_CONTROL | Înlocuit cu actualizare mascată și o citire diagnostică per port; erorile I/O și citirile all-ones continuă să oprească pornirea |
| P0 | „One-shot” nu descrie execuția: ETW arată șase încercări | Candidatul cere `WdfDeviceFailedNoRestart` la eșecul callbackurilor lifecycle D0 și post-interrupt; runnerul numără încărcările driverului și intrările firmware |
| P0 înainte de probă DMA | Eliberarea automată a obiectelor părinte WDF nu era acoperită la un stop DMA persistent eșuat | Adăugat cleanup software numai la EvtDeviceReleaseHardware, după închiderea accesului hardware și drenarea DPC/work-item; testate stop RUN blocat și eșecuri IRQ Enable/Disable |
| P1 | Fallback-ul Intel există numai pe calea normală; lipsește în recovery după eșec | Adăugat în `finally`, o singură încercare cu INF-ul exportat înainte de bind, după eliminarea pachetului M1; se disting tentativa și apelul reușit |
| P1 | Eșecul din WaitTelemetry nu salvează toate proprietățile dispozitivului înainte de rollback | Adăugată captură în catch-ul tranzacției, înaintea recuperării |
| P1 | `Stopped=true` era setat chiar dacă oprirea ETW eșua | Starea se setează numai după cod de ieșire zero; o eroare diagnostică nu mai întrerupe recovery în finally |
| P1 | JSON-ul Get-WinEvent are Message null; datele utile există în XML | Adăugată decodare a elementelor XML `Event/Data`, statistici și verificarea pierderilor ETW |
| P1 | Captura ETW se termina înaintea rollback-ului, fără cleanup pe calea de succes | Captura rămâne activă până după rollback; validarea dovezii de boot se face la sfârșit |
| P1 | Hash NHLT prezentat fără măsurare live în R7 | Candidatul marchează explicit `DECLARED_REFERENCE_ONLY`, cu hash observat null |
| P2 | README amestecă etape istorice și atribuiri neconfirmate de amplificator/rutare | Actualizat: nu se presupune MAX98357A/SSP1 pe baza acestui rezultat |
| P2 | Testele vechi modelează registrele SSP cu revenire perfectă a scrierilor | Adăugată o regresie independentă cu citire zero, plus cazuri de integrare |

Reîncercarea PnP este o inferență susținută de sursă și de cele șase cicluri ETW. Microsoft documentează reenumerarea/reîncărcarea după callbackuri eșuate și metoda `WdfDeviceSetFailed(...NoRestart)` pentru prevenirea ei [S6]. Patch-ul acoperă cele două ramuri menționate; nu pretinde că previne orice restart posibil din toate callbackurile, din managementul de alimentare sau din acțiuni externe. Numărarea ETW detectează încălcarea cerinței, fără să poată anula o încercare deja produsă.

Candidatul adaugă valori SSP etichetate cu portul și adresa, masca nepotrivirilor și ultimul offset MMIO. Datele SSP sunt colectate în timpul inițializării și emise după revenirea acesteia. Se adaugă separat stările opririi DMA, opririi DSP și închiderii HDA/PCI. Nu se modifică verificările reale ROM DONE, INIT_DONE, firmware entry sau FW_READY și nu se adaugă activare codec/amplificator ori playback.

Identitățile sunt coerente în INF, runner, CMD și workflow: versiunea `0.6.15.137`, build `m1-fast-safe-20260926-r8-candidate-ssp-contract`, prefix ETW `PHASER360_R8_CANDIDATE`. Acestea identifică o modificare de comportament față de R7. SYS-ul R8 compilat are SHA-256 `e417386ae3dff60b94ac1c4449c5f0333b53a7490d49b1e86b2ee4b7f3cba4c0`.

Cleanup-ul de removal se bazează pe contractul documentat EvtDeviceReleaseHardware: întreruperile sunt deconectate, dispozitivul este oprit și MMIO nu mai este permis [S12]. Calea timpurie din PrepareHardware nu poate invoca acest cleanup. Dacă oprirea DMA eșuează în D0, bufferele sunt păstrate până la limita framework-ului; la această limită se închid utilizatorii software și se lasă WDF să elimine obiectele copil. Păstrarea unui handle local nu ar împiedica disposal-ul părintelui. Testele verifică absența MMIO și PCI I/O în cleanup-ul final, drenarea lucrului amânat și păstrarea bufferelor până la teardown-ul framework-ului. Aceasta validează implementarea contractului software, fără a simula fidel întreaga platformă fizică. Nu s-au adăugat scrieri în PCI Command/BME; controlul antetului PCI aparține sistemului [S15].

## Firmware și limitele dovezii

Fișierul oficial SOF 1.9.3 fixat în proiect a fost comparat independent. Are 287488 octeți, același SHA-256 și apare integral în SYS-ul R7 la offsetul de fișier 65440. XMan ocupă 768 octeți, iar payloadul este de 286720 octeți. Proveniența fixată este `sof-bin` commit `a973fdba7a3555899ba3e58f89be3c258cf2a166`, fișier `sof-apl.ri` [S7].

Aceasta confirmă egalitatea octeților, nu acceptarea lor de ROM. Parserul declară `SIGNATURE_VERIFICATION=NOT_PERFORMED`; Authenticode nu a fost reverificat local prin API Windows. Traseul R7 nu ajunge la transfer, deci nu demonstrează un firmware respins. Nu există motiv susținut de aceste date pentru schimbarea imaginii în această corecție.

Hashul NHLT `4764aba0316e9a039a127285cc4ff9e97e22c75bfddb6d865d9f77b59dd2a6b9` este o referință declarată în runner/manifest. Rezultatul nu conține o nouă captură NHLT brută. Identitatea codec-ului, amplificatorul și rutarea audio trebuie fundamentate pe dovezi curente înaintea dezvoltării ieșirii audio.

## Ce trebuie făcut în continuare, în această ordine

1. Corecția de sursă este publicată, iar identitatea R8 rămâne distinctă de R7. Pentru probă se folosește arhiva binară din buildul final indicat mai sus, nu arhiva inițială cu patch-ul de surse.
2. Parserul PowerShell 5.1, testele simulate de recovery/ETW, verificările statice, compilarea WDK și verificările de pachet au trecut pe commitul final.
3. Cazul de stop DMA persistent eșuat are acum cleanup la limita EvtDeviceReleaseHardware și regresii explicite. Este important că D0Entry eșuat nu este urmat de D0Exit [S12, S13]. R7 nu a pornit HDA RUN; comportamentul fizic al următoarelor etape va fi verificat din noua captură.
4. Înainte de probă, verificarea baseline-ului efectiv și a platformei: acest rezultat este pentru build 19044 și Intel 9.22.0.4832/oem14.inf. Un sistem schimbat necesită o nouă bază de dovezi, nu relaxarea arbitrară a condițiilor. Completarea inventarului NHLT/ACPI se face separat, prin citire.
5. O probă fizică M1 cu ETW de la început, aceleași interdicții și rollback automat. Dovezi cerute: exact o intrare firmware, port/offset/readback SSP, ROM DONE și INIT_DONE, firmware entry și FW_READY validate, două citiri de telemetrie stabile, oprire DMA/DSP/HDA confirmată și restaurarea Intel/certificatelor. Dacă apare altă primă eroare, se investighează acea etapă; nu se declară succes doar fiindcă G75 a fost depășit.
6. Numai după un M1 demonstrat se continuă către audio: topologie și pipeline SOF, DAI/SSP pentru hardware-ul identificat, integrare codec/amplificator, endpoint Windows WaveRT/PortCls/KS și DMA PCM, apoi alimentare și suspend/resume. Rularea M1 este temporară și revine intenționat la Intel; nu poate oferi singură sunet permanent.

Rămân și cazuri de întărire a tranzacției în jurul publicării parțiale a INF-ului sau adăugării parțiale de certificate: bookkeeping-ul bazat numai pe succesul comenzii nu demonstrează recuperarea fiecărei mutații parțiale. Patch-ul livrat nu revendică rezolvarea completă a acelor scenarii. Rezultatul curent arată însă explicit un rollback reușit.

Timestampurile XML au fost păstrate textual: conțin offsetul `+02:59`, în timp ce alte fișiere folosesc `+03:00`. Auditul folosește ordinea evenimentelor și nu deduce durate precise prin amestecarea acestor reprezentări.
